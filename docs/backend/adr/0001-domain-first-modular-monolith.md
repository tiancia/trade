# ADR-0001：采用业务域优先的模块化单体

- 状态：已接受
- 日期：2026-07-17
- 决策范围：`backend/`

## 背景

后端同时承载交易、Polymarket、小说生成、文字游戏、集市、微博发布和后台任务编排。它们共享 Spring Boot 运行时、MySQL、部分外部客户端和运维方式，但业务模型、失败边界和迭代节奏不同。

若按全局 `controller/service/mapper` 技术层组织，一个需求会跨越多个大目录，模块所有权不清晰，跨域引用也容易增长。立即拆分成多个独立服务或 Maven 模块则会引入部署、事务、配置和联调成本，而当前规模尚不需要这些成本。

## 决策

采用单进程、单构建的模块化单体，并遵循：

1. 一级包按业务域划分：`trading`、`polymarket`、`story`、`textgame`、`marketplace`、`weibo`；
2. 每个业务域内部按需要使用 web、application、model/domain、persistence、config 等层；
3. `automation` 只做跨域生命周期编排；
4. `client`、`ai`、`common` 是共享基础能力，禁止反向依赖业务域；
5. 业务域之间不直接 import，需要共享时先确认是跨域编排、稳定共享契约，还是边界划分错误；
6. 使用架构测试锁定稳定边界，历史代码按业务变更渐进收敛，不做无业务收益的全量搬包。

## 结果

收益：

- 一个功能的入口、用例、规则、适配器和测试集中在同一域；
- AI 和新维护者可以先定位模块，再追踪局部调用链；
- 共享代码和跨域耦合有明确审查点；
- 保留单体部署、进程内调用和本地事务的简单性；
- 将来若某个域需要独立部署，已有边界可作为拆分起点。

代价：

- 包边界依赖代码评审和架构测试持续维护；
- 单一构建仍会编译和测试整个后端；
- 现有 marketplace、textgame 和部分 trading 路径仍有 application/domain 直接依赖 persistence adapter 的渐进债务；
- 共享数据库使物理数据边界弱于独立服务，表所有权必须靠约定维持。

## 未选择的方案

### 全局技术分层

不采用全局 controller/service/mapper 目录，因为它隐藏业务边界，并让每次修改横跨整个代码树。

### 立即拆成微服务

不采用。当前部署和团队规模下，网络协议、分布式事务、服务发现和独立运维的成本高于收益。

### 立即拆成多个 Maven module

暂不采用。Java 包边界和架构测试足以保护当前依赖方向；当模块需要独立发布、构建时间不可接受，或包级约束长期无法阻止越界时再重新评估。

## 演进触发条件

出现以下任一情况时新增 ADR 重新评估物理拆分：

- 某业务域需要独立扩缩容或发布节奏；
- 必须隔离数据库或故障域；
- 全量构建时间持续影响交付；
- 跨模块 API 已稳定且进程内调用不再带来明显收益；
- 合规要求需要单独部署或访问控制。
